# 使用说明

---

## 一、这是什么

一个校园公告资讯发布系统，给「有公告要发的人」和「要看公告的人」两类角色用。

- **前台**：资讯列表页（分页）+ 资讯详情页，任何人可看，只显示已发布内容
- **管理端**：发布 / 编辑 / 删除面板，能看到草稿，草稿排在资讯列表最前面
- **后端**：PHP 单入口 REST API，提供资讯的增删改查与分页

三个部分是**彻底分离**的：前端只通过 `fetch` 拿 JSON，后端只返回数据、不返回一个 HTML 标签。所以前端可以换成任何技术栈，后端不用动。

---

## 二、环境要求

| 项       | 版本                     | 备注                                             |
| ------- | ---------------------- | ---------------------------------------------- |
| PHP     | 7.4 及以上（实测 7.4.33 NTS） | 必须启用 `pdo_mysql`、`mbstring`、`json` 三个扩展        |
| MySQL   | 5.7 及以上（实测 5.7.26）     | 字符集用 `utf8mb4`                                 |
| Web 服务器 | PHP 内置服务器（开发用）         | 生产可换 Apache / Nginx，需把请求重写到 `public/index.php` |
| 浏览器     | Chrome / Edge 新版       | 前端用了 `fetch` 与 `async/await`，IE 不支持            |

检查扩展是否开启：

```bash
php -m | findstr /i "pdo_mysql mbstring json"
```

三个都出现才继续。缺 `mbstring` 会导致标题长度校验（`mb_strlen`）报错。

## 三、安装与启动

### 3.1 拿到代码

```bash
git clone https://github.com/hashbri/notice-board.git
cd notice-board
```

### 3.2 装依赖

**不需要装依赖。**

本项目做到零第三方依赖：

- 后端是 PHP 原生 + PDO，没有用框架，不生成 `composer.json`，**不需要 `composer install`**
- 前端是纯 HTML / CSS / 原生 JS，没有构建步骤，**不需要 `npm install`**

所以跳过这一步。

### 3.3 配置数据库

**第一步：建库 + 建表 + 导入示例数据**

`schema.sql` 里已经包含 `CREATE DATABASE`，不用手动建库：

```bash
mysql -u root -p < backend/sql/schema.sql
```

也可以用 phpMyAdmin：打开 SQL 标签页 → 粘贴文件内容 → 执行。

> ⚠️ 脚本开头有 `DROP TABLE IF EXISTS articles`，**重复执行会清空已有数据**，已有真实数据时别乱跑。

脚本会建一张 `articles` 表并插入 14 条示例数据，其中特意留了两条"哨兵"：

- `id=13`：`status=0` 的草稿
- `id=14`：已软删除（`deleted_at` 非空）

这两条用来验证"前台看不到、管理端能看到"这套权限区分是否生效。

**第二步：改数据库账号密码**

打开 `backend/public/index.php`，第 14 行：

```php
$pdo = new PDO('mysql:host=127.0.0.1;dbname=notice_board;charset=utf8mb4', 'root', 'root', [
```

把两个 `'root'` 换成你自己的 MySQL 账号和密码。第一个是用户名，第二个是密码。

> ⚠️ **这里是硬编码，没有抽到 `.env` 配置文件。** 换机器要改代码，属于本项目已知不足之一，改进方向见 [README](../README.md#已知不足)。

### 3.4 启动

要开**两个**终端窗口，一个跑后端、一个跑前端。

> **最快的方式**：按顺序双击 `tools/` 下的 `1-start-db.bat` → `2-start-api.bat` → `3-start-web.bat`，三个窗口都保持打开即可。脚本会自动查端口、找 PHP 路径。
>
> 下面讲的是这些脚本**内部实际执行的命令**——搞清楚原理，脚本出问题时你才知道怎么查。

**窗口 1 —— 后端**

```bash
cd backend
php -S localhost:8000 -t public public/router.php
```

看到 `Listening on http://localhost:8000` 就成了，别关这个窗口。

**`public/router.php` 不能省。** 因为接口地址是 `/api/articles/19` 这种"不存在的文件路径"，PHP 内置服务器默认会去磁盘上找同名文件，找不到直接 404。`router.php` 的作用是把所有请求都交给 `index.php` 处理。生产环境用 Apache/Nginx 时要配 `RewriteRule` 做同一件事。

**窗口 2 —— 前端**

```bash
cd frontend
php -S localhost:5500 -t .
```

然后浏览器打开：

```
http://localhost:5500/index.html
```

**前端也必须用服务器打开，不能双击 HTML 文件。** 两个原因：

1. 双击走的是 `file://` 协议，`fetch` 请求会被浏览器的跨域策略直接拦掉
2. 前端在 5500、后端在 8000，端口不同就算跨域，正好能验证后端的 CORS 配置是不是真的生效

### 3.5 验证跑通了

先做这四步，全过说明基本跑通了：

| # | 检查项                                        | 期望结果                                       |
| - | ------------------------------------------ | ------------------------------------------ |
| 1 | 浏览器打开 `http://localhost:8000/api/articles` | 返回 `{"code":0,...}`，`data.total` 等于你的已发布条数 |
| 2 | 打开 `http://localhost:5500/index.html`      | 列表显示 5 条公告，底部「第 1 / N 页」（N 为总页数）           |
| 3 | 点第一条标题                                     | 跳转详情页，正文完整，段落换行保留                          |
| 4 | 点右上角「管理端」→ 填标题正文 → 提交                      | 提示「发布成功，id = N」，列表立刻多一条                    |

再补两个关键检查（证明权限区分有效）：

| # | 检查项 | 期望结果 |
| - | --- | --- |
| 5 | 管理端第 1 页，找到带「草稿」标签的条目 | 前台列表里搜不到它，管理端能看到 |
| 6 | 前台地址栏手动输入 `http://localhost:8000/api/articles/13` | 返回 `404` + `{"code":1002,"message":"文章不存在"}` |

第 6 步最容易漏。它证明的是：**草稿不是"前端没显示"，而是后端真的不给**。改前端代码也绕过不了。

## 四、怎么使用

以下操作假设第三节的两个窗口都在跑，浏览器已打开 `http://localhost:5500/index.html`。

### 4.1 看公告（访客视角，不需要登录）

打开 `http://localhost:5500/index.html`。

- 标题下方显示「**共 N 条**」。这个 N 只统计**已发布**的，草稿不算在内。
- 每页 5 条，只显示标题，不显示正文和时间。
- 点任意一条标题 → 进入详情页。
- 底部是分页条：`上一页` ｜ `第 1 / 3 页` ｜ `下一页`

**翻页效果**：点「下一页」，列表整体换成接下来的 5 条，页码同步变成 `第 2 / 3 页`。再点一次换第 3 页。**页与页之间不重复、不遗漏**——因为后端排序带了 `id DESC` 兜底，同一秒发布的两条也不会乱序。

**边界处理**：在第 1 页时「上一页」是灰的、点不动；在最后一页时「下一页」是灰的。这比"点了没反应"更明确——用户能看见自己在哪里。

### 4.2 看某一篇的详情

点标题后，地址栏会变成：

```
http://localhost:5500/detail.html?id=19
```

**为什么是 `?id=19` 而不是 `detail.html/19`？** 因为这是纯静态页面，没有服务端路由。两个 HTML 文件之间唯一的传参方式就是 URL 里的查询参数。列表页点标题时把 `item.id` 拼进地址，详情页用 `new URLSearchParams(location.search).get('id')` 取出来，再拿这个 id 去请求后端。

详情页显示三部分：标题、`发布于 2026-11-20 14:23:18`、正文（**保留原来的换行**）。左上角「← 返回列表」回到列表页。

如果 id 不存在，或者那篇是草稿，页面会显示「文章不存在 / 该公告可能已被删除，或链接有误」。

### 4.3 发布一条新公告

1. 列表页**右上角**点「管理端」，进入管理端页面（不用记网址，也不需要手动输入）。
2. 在「发布公告」表单里填：
   - **标题**：不超过 100 字（输入框本身限制住了）
   - **正文**：随便写多长，换行会保留
   - **状态**：选「发布（前台可见）」
3. 点「提交」。
4. 提示「发布成功，id = N」，下方「文章管理」列表立刻刷新，新条目出现在最前面。

**校验规则（前后端各拦一道）**：

| 规则 | 前端 | 后端 |
|---|---|---|
| 标题不能为空 | 有，不通过不发请求 | 有，`trim` 后判空 |
| 正文不能为空 | 有 | 有 |
| 标题不超过 100 字 | `maxlength="100"` 输不进去 | `mb_strlen` 兜底 |
| 状态只能是 0 或 1 | 下拉框只有两项 | 白名单判断 |

为什么要拦两遍？**前端拦是为了体验**（不用等网络往返就知道错了），**后端拦是为了安全**（绕过前端直接发请求，照样拦得住）。只做前端等于没做。

### 4.4 存草稿（先不发布）

步骤和 4.3 完全一样，只有一个区别：**状态下拉选「存草稿（前台不可见）」**。

存完之后你会看到两个现象：

- **前台列表看不到它**，「共 N 条」不会增加。
- **管理端看得到**，标题右边多一个灰色小框「草稿」，而且**排在第 1 页最上面**。

为什么排最前面？管理端列表的排序是 `status ASC, created_at DESC, id DESC`。`status` 升序让 0（草稿）全部排在 1（已发布）前面。这是后台系统的常见做法——**待办优先**，管理员一进来就先看到还没发出去的东西。

**草稿想变成正式公告**：在管理端点它的「编辑」，把状态改成「发布（前台可见）」，再点「提交」。见下一节。

### 4.5 编辑一篇已有公告

1. 进管理端。
2. 在「文章管理」列表里找到目标（草稿都在第 1 页最上面）。
3. 点这一行右侧的 **「编辑」** 按钮。
   > 注意：**点标题不会触发编辑**。标题是纯文本，只有按钮能点——这样你在列表上是安全的，不会误点进编辑状态。
4. 表单上方的标题变成「编辑公告 #19」，标题、正文、状态下拉都被**自动填好**，同时旁边多出一个「取消编辑」按钮。
5. 改内容，点「提交」，提示「修改成功，id = 19」。

**两个容易困惑的地方，提前说清**：

**① 只有一个提交按钮，它怎么知道是新增还是修改？**

管理端用一个变量 `editingId` 记着"当前在编辑谁"。它是 `null` 时发 `POST /api/admin/articles`（新增）；点过「编辑」之后它变成具体 id，提交时就改成 `PUT /api/admin/articles/19`（修改）。所以你不用记两个按钮，也不用担心点错。

**② 把草稿改成「发布」提交后，它从第 1 页消失了**

**它没被删。** 它从 `status=0` 那一组跳到了 `status=1` 那一组，按 `created_at` 重新排队，位置挪到后面去了。往后翻页能找到。

这是「草稿优先排序」的必然代价，属于设计取舍，不是 bug。

**③ 「取消编辑」是干嘛的**

不想改了、或者想知道自己刚才点了哪一篇，按它：表单清空、标题回到「发布公告」、`editingId` 归 `null`，回到"新增"状态。

### 4.6 删除一篇公告

1. 管理端找到目标条目。
2. 点「删除」。
3. 浏览器弹窗：「确定删除这篇公告吗？删除后前台将不再显示。」点确定。

删除是**软删除**：数据库里那条记录还在，只是 `deleted_at` 被填上了当前时间。前台列表、管理端列表、两者查详情的 SQL 全都带 `deleted_at IS NULL`，所以删完之后三处都查不到它。

好处是**误删能救回来**，恢复方法见 Q7。坏处是表会越来越大，需要定期清理——这是软删除的固有代价，写在这里是为了让你知道它存在。

### 4.7 草稿 vs 已发布：一张表说清

| | 草稿 `status=0` | 已发布 `status=1` |
|---|---|---|
| 前台列表页 | 不出现 | 出现 |
| 前台详情（手动输 id 访问） | **404 + 文章不存在** | 正常显示 |
| 管理端列表 | 出现，挂「草稿」标签，**排最前** | 出现，按时间倒序 |
| 管理端详情 | 正常读到 | 正常读到 |
| 接口路径 | 必须走 `/api/admin/articles/{id}` | 两条路径都行 |
| 能否互相转换 | 能，编辑时改状态下拉 | 能，同上 |

这张表能回答「为什么我发布了却看不到」这一类问题：**先确认它的 `status` 到底是 0 还是 1。**

注意最后一行和倒数第二行的区别：**"能不能看到"由 `status` 决定，而"从哪个地址能看到"由接口路径决定。** 前者是数据属性，后者是访问权限，两个概念别混。

## 六、常见问题

### Q1：启动后端后一访问就报 `SQLSTATE[HY000] [2002] 目标计算机积极拒绝`

**MySQL 没启动。** 打开任务管理器看有没有 `mysqld.exe`，或在 phpstudy 里点「启动」。

### Q2：`Address already in use` / `端口已被占用`

8000 或 5500 被别的程序占了。要么关掉那个程序，要么换端口：

```bash
php -S localhost:8001 -t public public/router.php
```

**换端口后必须同步改前端。** 三个 HTML 文件里都写着 `http://localhost:8000/api/...`，后端换到 8001 了，前端不改就全部请求失败。

> **双击启动脚本，提示「端口已占用」但你根本没开过服务？**
>
> 多半是 `TIME_WAIT` 残留。TCP 连接关闭后，套接字会在系统里再停留约 2 分钟，这段时间 `netstat` 仍然显示这个端口，但状态是 `TIME_WAIT` 而不是 `LISTENING`——**没有任何进程在监听它**。
>
> `tools/` 下的脚本已经加了一层 `findstr "LISTENING"` 过滤来排除这种情况。你自己写的脚本如果只判断端口号，就会在「刚关掉服务又立刻重开」时把自己挡在门外。详见 `design.md` 第 6 节坑 4。

### Q3：页面能打开，但列表是空的，F12 控制台报 CORS 错误

按顺序查：

1. 后端窗口是不是已经关了
2. 浏览器地址是不是 `http://localhost:5500` 开头（`file://` 开头一定失败）
3. `index.php` 最前面那 5 行 CORS 头还在不在

### Q4：发布成功了，但前台列表里找不到

**大概率是设成了草稿。** `status=0` 的内容前台按设计不显示，去管理端看，它排在第 1 页最前面。

如果确认是「发布」（`status=1`）还看不到，检查是不是在分页的后面几页。

### Q5：中文显示成 `???` 或乱码

三处字符集必须一致：

- 建库：`DEFAULT CHARACTER SET utf8mb4`
- 连接：`charset=utf8mb4`（在 `index.php` 第 14 行的 DSN 里）
- 页面：`<meta charset="utf-8">`

任何一处写成 `utf8`（少了 `mb4`），emoji 就会存不进去。

### Q6：管理端点「编辑」提示「加载失败：文章不存在」

管理端读详情必须走 **`/api/admin/articles/{id}`**。如果走了 `/api/articles/{id}`，草稿会被后端判定为"不存在"——这是设计如此，不是 bug。

### Q7：想恢复一条被删掉的公告

删除是**软删除**，数据还在表里，只是 `deleted_at` 有值。恢复它：

```sql
UPDATE articles SET deleted_at = NULL WHERE id = 你那条的 id;
```

这是软删除的好处：误删能救回来，普通 `DELETE` 就真没了。

## 七、开发说明

### 重置数据

重跑 `backend/sql/schema.sql`，会清空表并重新插入 14 条示例数据。

### 接口自测面板

`backend/public/_test_api.html` 是一个临时调试页，用浏览器打开可以对 5 个接口逐个发请求、看原始响应，不用手写 `curl`。它跟主流程无关，正式部署时删掉即可。

### 改每页条数

- 前台：`index.html` 里请求的 `?page=` 后面没带 `size`，用后端默认值 5
- 管理端：`admin.html` 顶部的 `var ADMIN_SIZE = 5;`
- 上限：后端限制 `size` 最大 50，传超了会自动回落到 5
