## 1. 为什么前后端分离

**谁调谁**：浏览器里的页面通过 `fetch` 调用后端 HTTP 接口，接口只返回 JSON。后端不生成任何 HTML，也不知道页面长什么样。

```
前端页面  --fetch(JSON)-->  index.php  --PDO-->  MySQL
          <--JSON---------
```

### 好处

| 好处 | 在本项目中的具体体现 |
|---|---|
| 职责单一 | `index.php` 里没有一行 HTML，全是取数据、校验、返回 JSON；页面里没有一行数据库代码 |
| 接口可独立测试 | 浏览器直接访问 `/api/articles` 就能看到结果，不必先有页面。5 个接口在前端尚未存在时已全部验证通过 |
| 换前端不用动后端 | 后续要做小程序或重做 UI，后端一行不改 |
| 问题定位快 | 接口返回正确而页面不对 → 问题必在前端；接口本身就错 → 问题在后端。不用两头猜 |

### 代价

| 代价 | 说明 |
|---|---|
| 需额外定义接口契约 | 字段名、响应结构、错误码必须约定死，否则前端无从下手。这是 `api.md` 存在的理由 |
| 前端承担更多工作 | 渲染列表、加载状态、错误提示全部手写，框架不提供 |
| **`$_POST` 失效** | 发 JSON 时 PHP 不自动解析请求体，必须 `file_get_contents('php://input')`（见坑 2） |
| 跨域限制 | 前后端不同端口或域名时须加 CORS 响应头，否则被浏览器直接拦截 |

### 我的取舍

本项目只有一组页面、12 条数据，从复杂度看**完全可以写成"PHP 直接 echo HTML"的传统模式**，代码量更少。

选分离的理由不是"分离更先进"，而是：**这个项目要练的是接口设计能力**——路由分发、统一响应结构、错误码体系、分页参数，这些在传统模式里根本不会出现。而且分离之后，第 2、3、6 节讨论的所有问题才成立。

代价是可控的：接口只有 5 个、响应结构只有一种，写清 `api.md` 即可；跨域在开发阶段用同源部署规避（测试页与后端同在 `localhost:8000`）。

## 2. 数据库表设计

### 2.1 表结构

| 字段 | 类型 | 约束 | 为什么这么定 |
|---|---|---|---|
| `id` | `INT UNSIGNED` | `NOT NULL AUTO_INCREMENT`，主键 | 无业务含义的自增主键。不用标题当主键——标题会改，一改所有引用和 URL 全断 |
| `title` | `VARCHAR(100)` | `NOT NULL` | 有明确上限。100 这个数字在三处对齐：建表 `VARCHAR(100)`、后端 `mb_strlen > 100` 校验、前端 `maxlength="100"` |
| `content` | `TEXT` | `NOT NULL` | 见 2.2 ① |
| `status` | `TINYINT` | `NOT NULL DEFAULT 0` | 见 2.2 ② |
| `created_at` | `DATETIME` | `DEFAULT CURRENT_TIMESTAMP` | 由数据库生成，**不信任前端传时间** |
| `updated_at` | `DATETIME` | `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` | 同上。用 `ON UPDATE` 自动维护，不写触发器也不用应用层代码 |
| `deleted_at` | `DATETIME` | `NULL DEFAULT NULL` | 非空 = 已软删除，见 2.2 ③ |

引擎 `InnoDB`（要事务和行锁），字符集 `utf8mb4`（要能存 emoji，`utf8` 存不了）。

### 2.2 四个关键决策

**① `content` 用 `TEXT`，不用 `VARCHAR` 也不用 `LONGTEXT`**

| 方案 | 上限 | 为什么不选 |
|---|---|---|
| `VARCHAR(2000)` | 2000 字符 | 公告正文长度不可预知，定死一个值早晚要 `ALTER` |
| `LONGTEXT` | 4 GB | 上限大到可以塞进一个文件，**掩盖"该用附件却塞进字段"的错误用法** |
| **`TEXT`** ✅ | 64 KB | 一篇公告几百到几千字，64 KB 有两个数量级余量，同时上限又小到能提醒人「这不是放文件的地方」 |

选型逻辑不是"越大越好"，而是**上限本身是一句约束声明**。

**② `status` 用 `TINYINT` + 应用层白名单，不用 `ENUM`**

| 方案 | 新增一个状态 | 风险 |
|---|---|---|
| `ENUM('draft','published')` | 必须 `ALTER TABLE` 改表结构，生产环境是锁表重操作 | 改表期间写入阻塞 |
| **`TINYINT` + 后端白名单** ✅ | 加一个值不用改表 | 数据库本身不拦脏值，得靠应用层 |

取舍：**表结构稳定性优先于"数据库层强约束"。** 状态种类在业务演进中是最容易变的东西（以后可能加「置顶」「归档」「审核中」），每加一个都要 `ALTER` 是负担。

代价必须正视：`TINYINT` 存得下 `7`，数据库不会拦。所以后端那道 `$status !== 0 && $status !== 1` 白名单**不是可选项**，它是这套设计的补丁。

**③ 软删除用 `deleted_at` 时间戳，不用 `is_deleted` 布尔**

| 方案 | 能回答「删了吗」 | 能回答「什么时候删的」 | 空间 |
|---|---|---|---|
| `is_deleted TINYINT(1)` | ✅ | ❌ | 1 字节 |
| **`deleted_at DATETIME`** ✅ | ✅（非空即删） | ✅ | 5 字节 |

多花 4 字节，换来一个可查询的时间维度。排查问题经常是「这批数据什么时候消失的」，布尔值答不上来。

**④ `created_at` / `updated_at` 交给数据库，不用 PHP 生成**

理由只有一个但足够：**服务器时区、应用时区、数据库时区可能三者不一致**。PHP 生成的时间串值取决于 `date_default_timezone_set` 有没有配对，数据库生成的时间由数据库自己的时区决定。让一个地方说了算，比三个地方各说一次可靠。

### 2.3 索引：为什么是 `(status, deleted_at, created_at)`

```sql
KEY idx_list (status, deleted_at, created_at)
```

按**最左前缀原则**，这个联合索引能完整服务前台列表的查询：

```sql
WHERE status = 1 AND deleted_at IS NULL ORDER BY created_at DESC, id DESC
```

- `status`、`deleted_at` 两列**等值匹配** → 精确圈出"已发布且未删除"那一段
- `created_at` 是索引第三列，且排序方向一致（DESC）→ **按索引顺序取出即为有序，不需要额外排序**
- 排序里的 `id DESC` 不用建进索引：InnoDB 二级索引的叶子节点自带主键，等价于索引是 `(status, deleted_at, created_at, id)`

实测 `EXPLAIN`：

```
type:  ref            ← 走索引，不是全表扫描
key:   idx_list       ← 用上了
rows:  14
Extra: Using where    ← 注意：没有 Using filesort
```

`Extra` 里**没有** `Using filesort`，说明排序完全由索引完成，没有额外的排序内存和时间开销。这是建这个联合索引最直接的回报。

### 2.4 一个已知的索引缺口（管理端）

管理端列表的排序和前台不同：

```sql
WHERE deleted_at IS NULL ORDER BY status ASC, created_at DESC, id DESC
```

`EXPLAIN` 结果：

```
type:  ALL                        ← 全表扫描
key:   NULL                       ← 一个索引都没用上
rows:  20
Extra: Using where; Using filesort
```

**原因**：`WHERE` 里只有 `deleted_at`，而 `idx_list` 第一列是 `status`。最左前缀原则要求从第一列开始连续匹配，跳不过去，整个索引作废。

**现在为什么不修**：全表 20 行，全扫描的代价是可忽略的常数。加一个 `(deleted_at, status, created_at)` 索引能让它走索引，但在 20 行的数据量下性能差异落在测量噪声里——**为看不出差别的东西改表结构，是假优化**。

**什么时候必须修**：数据量到万级，或管理端页面出现肉眼可感的卡顿。到时执行：

```sql
ALTER TABLE articles ADD KEY idx_admin (deleted_at, status, created_at);
```

这条已经写进第 7 节已知不足，带着触发条件。

## 3. 分页方案

> 作业只要求"实现分页"。这里写清**你选的是哪一种、为什么、边界在哪**。

| 方案 | 原理 | 优点 | 缺点 | 我选了吗 |
|---|---|---|---|---|
| `LIMIT offset, size` | 跳过前 offset 条，取 size 条 | 实现简单；可直接跳到第 N 页 | offset 越大，数据库需扫描并丢弃的行越多 | ✅ **采用** |
| 游标分页（cursor） | 从上一页最后一条的位置往后取 | 深翻页也快，与页码无关 | 不能跳页；要求排序键严格稳定（见坑 1）；接口要传 cursor 而非 page | ❌ |

### 我选的方案

`LIMIT offset, size`，其中 `offset = (page - 1) * size`。

```php
$page   = max(1, (int)($_GET['page'] ?? 1));
$size   = 5;
$offset = ($page - 1) * $size;
```

`max(1, ...)` 是边界兜底：`?page=0` 或 `?page=-3` 会被拉回第 1 页，避免拼出负 offset。

### 理由

1. **数据量小**。当前 14 条已发布数据，每页 5 条，共 3 页。offset 最大为 10，需要扫描并丢弃的行数可忽略——offset 分页的线性代价在这个规模下不存在。
2. **需要跳页**。用户要能直接点"第 3 页"，游标分页必须从头翻，做不到。
3. **接口形状简单**。`?page=2` 一个整数参数就够；游标分页要维护 cursor、处理"cursor 失效"，复杂度高一个量级。

### 边界：什么情况下该换掉

| 数据量 | 建议 |
|---|---|
| 万级以下 | `LIMIT offset` 完全够用（当前方案） |
| 十万级以上，且只翻前后页 | 换游标分页 |
| 十万级以上，且必须跳页 | 保留 offset，但限制最大可翻页数，或用覆盖索引减少扫描 |

### 一次列表请求的实际开销

- **执行 2 条 SQL**：`COUNT(*)` 取总数 + `SELECT` 取当前页。两条带完全相同的 `WHERE status = 1 AND deleted_at IS NULL`
- 为什么分两条：总数需跨全表统计，当前页只要 5 条，一条 SQL 无法同时给出。（`SQL_CALC_FOUND_ROWS` 在 MySQL 8.0 已标记废弃，不采用）
- 响应体只返回 `total / page / size`，总页数 `ceil(total / size)` 由前端计算，后端不重复计算

### 关于耗时对比

未做 offset=0 与 offset=10 的耗时对比：当前数据量仅 14 条，两者的差异落在测量噪声内，测出的数字不具参考价值。这个对比要等数据量上万才有意义。

## 4. 表单校验

> 关键问题：**前端校验和后端校验各做什么，为什么不能只做一边。**

### 4.1 后端实际实现的校验

新增（`POST /api/articles`）与修改（`PUT /api/articles/{id}`）共用同一套：

| # | 校验 | 拦截的情况 | 返回 |
|---|---|---|---|
| 1 | `!is_array($body)` | 请求体不是合法 JSON，或前端根本没发 body | `400` / `1001` |
| 2 | `trim($title) === ''` | 标题为空，**或内容全是空格** | `400` / `1001` |
| 3 | `mb_strlen($title) > 100` | 标题超过 100 个字符 | `400` / `1001` |
| 4 | `trim($content) === ''` | 正文为空 | `400` / `1001` |
| 5 | `$status !== 0 && $status !== 1` | 状态不是 0 或 1（枚举白名单） | `400` / `1001` |

### 4.2 前端做的是

- **即时反馈**：输入时就提示“标题不能为空”，不用等提交
- **减少无效请求**：明显不合法的表单不发给后端
- 本质是**用户体验优化**，不影响数据最终是否合法

### 4.3 后端做的是

- **唯一可信的合法性判定**。数据库前面只有这一道关
- 校验业务规则（长度上限、枚举取值），并且这些规则与建表时的字段约束保持一致

### 4.4 为什么后端必须再做一遍

前端校验**可以被随意绕过**，成本极低：

| 绕过方式 | 难度 |
|---|---|
| 按 F12 删掉 `required` 属性 | 3 秒 |
| 用命令行直接向接口发请求 | 一条命令 |
| 改 JS 把校验函数整个删掉 | 10 秒 |

**前端校验的定位是“帮用户少犯错”，不是“防止数据出错”。** 只有后端校验能保证进入数据库的数据合法，因为它离数据库最近，且不受客户端控制。

### 4.5 三个容易漏掉的细节

**① `trim()` 不能省**

```php
if ($title === '') { ... }        // "   "（三个空格）不等于 ''，能混过去
if (trim($title) === '') { ... }  // 先切掉首尾空格，才拦得住
```

用户只敲了空格时，`$title` 是非空字符串。**不做 `trim`，校验就是漏的。**

**② 中文长度必须用 `mb_strlen`**

| 函数 | 计的是 | `"你好"` 的结果 |
|---|---|---|
| `strlen()` | 字节数 | **6**（UTF-8 下一个汉字 3 字节） |
| `mb_strlen()` | 字符数 | **2** |

`title` 字段是 `VARCHAR(100)`，限制的是 **100 个字符**。若用 `strlen` 校验，中文写到 33 个字就被拦下，体验严重受损。`mb_` 是 multi-byte 的缩写。

**③ `status` 用白名单，不用范围判断**

```php
if ($status !== 0 && $status !== 1)   // ✅ 明确只允许这两个值
if ($status < 0 || $status > 1)       // ❌ 值域中间若有漏洞会漏掉
```

字段语义是“0=草稿，1=已发布”，中间没有其他取值。白名单能保证表里不会出现 `status = 7` 这种无人认识的脏数据。

### 4.6 校验失败时如何返回、前端如何显示

后端统一返回：

```json
{ "code": 1001, "message": "标题不能为空" }
```

同时 `http_response_code(400)`。**状态码给机器判断，`message` 给人看。**

前端处理方式（页面实现阶段落实）：按 `code` 分支判成败，把 `message` 直接显示在对应输入框下方——因为后端返回的 `message` 已经是可直接展示的中文文案，前端不需要自己维护一份错误文案表。

## 5. 权限 / 安全

> 这一节要诚实。本项目**没有登录功能**，所以第一个问题的答案直接是"没防"。
> 把缺陷写在自己文档里，比等别人指出来强。

### 5.1 管理端怎么防止未登录的人打开

**没防。** 任何人打开 `admin.html` 就能发布、编辑、删除。这是本项目**最大的安全缺陷**，明写在这里。

但有一个容易被混为一谈的区别要说清——**做了「数据隔离」，没做「访问控制」**：

| | 做了什么 | 防住了什么 | 没防住什么 |
|---|---|---|---|
| 数据隔离 | 前台接口强制 `status = 1`；草稿只能从 `/api/admin/articles` 读到 | 匿名访客看不到草稿内容 | 任何人只要知道 `/api/admin/` 这个前缀，一样读得到 |
| 访问控制 | **没做** | — | 任何人能以管理员身份增删改 |

所以 `/api/admin/` 这个前缀的价值**不是安全**，而是这两点：

1. **前台代码不可能误显示草稿。** 即使前端写错、忘了过滤，后端也不会给——防线在离数据最近的地方。
2. **以后加登录，只需给这一个前缀加一道门。** 前台 5 个接口的代码一行不用改。

**如果真要补登录，按代价从低到高**：

| 方案 | 做法 | 缺点 |
|---|---|---|
| HTTP Basic Auth | Web 服务器层校验，不用写代码 | 凭据明文传输，必须配 HTTPS |
| 固定 token | 登录后发随机串，管理端每个请求带 `Authorization` 头 | 泄露即失守，没有过期概念 |
| **Session** | `session_start()`，登录后存 `$_SESSION['admin']`，管理端接口先查它 | 前后端不同端口，要配跨域 cookie（`SameSite` / `credentials`） |
| JWT | 签名 token，服务端无状态 | 对 5 个接口的项目是过度设计 |

**结论**：作业没要求登录，现在不做。但这是**上生产前必须补的第一件事**，已列进第 7 节。

### 5.2 SQL 注入：怎么防的

所有 SQL 都是「占位符 + 参数分离」两步：

```php
$stmt = $pdo->prepare("SELECT ... FROM articles WHERE id = ?");
$stmt->execute([$id]);
```

`prepare` 把带 `?` 的 SQL 交给数据库**预编译**，`execute` 才传参数。参数永远被当作**值**，不会被重新当成 SQL 语法解析——`1 OR 1=1` 传进去只是一段普通字符串，改不了查询逻辑。

**关键选项：`PDO::ATTR_EMULATE_PREPARES => false`**

| 设置 | 行为 | 后果 |
|---|---|---|
| `true`（PHP 默认） | 预处理在 PHP 端**模拟**：参数转义后拼成完整 SQL 再发出去 | 类型信息丢失；`LIMIT ?, ?` 会被拼成 `LIMIT '0','5'` 报 1064 |
| **`false`**（本项目） | 交给 MySQL 真预处理 | 参数类型明确，`LIMIT ?` 这类语法位置也能正确工作 |

这个选项不是"优化项"，是**功能必需项**。不开它，分页根本跑不起来。

**有两处刻意保留的字符串拼接**：

```php
$where = $isAdmin ? "deleted_at IS NULL" : "status = 1 AND deleted_at IS NULL";
$order = $isAdmin ? "status ASC, created_at DESC, id DESC" : "created_at DESC, id DESC";
```

不违反规则，因为：**表名、列名、排序方向、条件结构无法参数化**——`ORDER BY ?` 本身就是语法错误，占位符替代不了结构。

安全性由另一件事保证：这两个变量只可能是**两个写死的常量之一**，由 `$isAdmin` 布尔值决定，用户输入一个字都进不来。

规则压缩成一句：**值用 `?` 绑定，结构用白名单拼。**

### 5.3 XSS：公告正文里的 HTML 怎么处理

**一律当纯文本，不当 HTML 渲染。**

前端所有用户数据都用 `textContent` 写入：

```js
span.textContent = item.title;   // ✅ 内容按纯文本处理
span.innerHTML   = item.title;   // ❌ 内容按 HTML 解析
```

差别有多大：

| | `textContent` | `innerHTML` |
|---|---|---|
| 标题是 `<img src=x onerror=alert(1)>` | 屏幕上原样显示这串字符 | 浏览器执行 `onerror`，弹窗 |

如果用了 `innerHTML`，**任何能发布公告的人都能在公告里埋脚本**，所有访客一打开列表页就执行——窃取 cookie、伪造页面、跳转钓鱼站。

这个风险在本项目里是**实打实的**，不是理论风险：管理端没有鉴权（5.1），意味着谁都能发布。

**代价**：正文不能写 HTML，加粗、链接、列表都不生效，换行靠 `.article-body` 上的 `white-space: pre-wrap` 保留。

这是主动放弃富文本，换取"不可能被注入脚本"。将来要支持富文本，正确做法是**服务端用白名单库过滤标签**（如 HTMLPurifier），而不是直接把 `textContent` 换成 `innerHTML`。

### 5.4 数据库密码放在哪

**当前状态：硬编码在 `backend/public/index.php` 第 14 行，且随代码一起提交到仓库。**

```php
$pdo = new PDO('mysql:host=127.0.0.1;...', 'root', 'root', [...]);
```

这是**明确的已知缺陷**，写在这里而不是遮起来。

为什么暂时能接受：

- 本地 MySQL 是 `root/root`，只监听 `127.0.0.1`，外网访问不到
- 仓库公开，但泄露的是一台**没有对外提供服务**的本地库密码

为什么上生产前必须改：

| 风险 | 说明 |
|---|---|
| 密码进了 Git 历史 | Git 历史不会因为删掉那行就消失，`git log -p` 照样翻得出来。真泄露了要**改密码**，改代码没用 |
| 环境切不了 | 开发/测试/生产三套库，密码写死就得靠改代码切换 |

**正确做法**（下一步计划）：

```
backend/
├── config.example.php   ← 提交，只有占位值
└── config.php           ← 真实密码，写进 .gitignore
```

`index.php` 改成 `require __DIR__ . '/config.php';`。仓库里只有模板，真实密码只存在于本机。

## 6. 踩过的坑（最重要的部分）

> 这里每条都值得写。面试官最爱追问的就是这一节。

### 坑 1：分页排序不稳定，同秒发布的数据会重复或遗漏

- **现象**：实现列表接口时检查了排序键的唯一性，提前加上第二排序键，未在实测中触发。
- **原因**：`created_at` 是 `DATETIME`，精度到**秒**。多条记录在同一秒发布时，`ORDER BY created_at DESC` 无法区分它们的先后——MySQL 对"排序值相同的行"**不保证返回顺序稳定**，同一条 SQL 执行两次可能给出不同顺序。

  这在分页时会造成实际问题：

  ```
  第 1 页  SELECT ... LIMIT 0, 5   → 顺序 A B C D E
  第 2 页  SELECT ... LIMIT 5, 5   → 若顺序变成 A C B D E
           则 B 在两页重复出现，C 被跳过
  ```

  顺序乱本身不致命，致命的是**两次查询之间顺序变了**，导致翻页重复或丢数据。

- **怎么修的**：加一个唯一的第二排序键。

  ```sql
  ORDER BY created_at DESC, id DESC
  ```

  为什么选 `id`：

  | 候选项 | 能不能兜底 | 原因 |
  |---|---|---|
  | `id` | ✅ | 主键，唯一且不随内容变化 |
  | `title` | ❌ | 两篇文章可以重名 |
  | `status` | ❌ | 只有 0 / 1 两个值，比 `created_at` 更容易撞 |

  `ORDER BY` 多键规则：**先按第一个键排，值相同时才看第二个**。所以 `created_at` 相同时，由唯一的 `id` 决定先后，结果完全确定。

- **如果重来会怎么避免**：写任何 `ORDER BY` 之前，先问一句"**这个排序键唯一吗？**"不唯一就补一个唯一键兜底，最省事的就是主键。

### 坑 2：前后端分离下，`$_POST` 拿不到 JSON 请求体

- **现象**：接口按前后端分离的方式实现，请求体统一用 JSON，服务端直接使用 `php://input` 读取，未使用 `$_POST`。
- **原因**：PHP **不是**永远解析请求体，它只对两种 `Content-Type` 自动解析并填入 `$_POST`：

  | `Content-Type` | 场景 | `$_POST` 可用吗 |
  |---|---|---|
  | `application/x-www-form-urlencoded` | 普通表单提交 | ✅ |
  | `multipart/form-data` | 带文件上传的表单 | ✅ |
  | `application/json` | `fetch` 发 JSON | ❌ `$_POST` 是空数组 |

  前端用 `fetch` 发 JSON 时，请求头是 `application/json`，PHP 不认识这个格式，因此不解析。数据仍在请求体里，只是没有被搬进 `$_POST`。

- **怎么修的**：

  ```php
  $raw  = file_get_contents('php://input');   // 请求体原文，一串 JSON 文本
  $body = json_decode($raw, true);            // 转成关联数组
  ```

  两个细节：

  - `php://input` 是只读流，通向本次请求的 body，与 `Content-Type` 无关
  - `json_decode` 的第二个参数 `true` 决定返回**关联数组**；省略则返回对象，取值要写成 `$body->title`

- **边界（这不是 PHP 的缺陷）**：`$_POST` 没有失效。传统 `<form method="post">` 提交时它照常工作。这是**选择 JSON 作为数据格式带来的连带后果**，不是框架问题。

- **如果重来会怎么避免**：在接口文档里显式写明"请求体为 JSON，服务端用 `php://input` 解析"，前后端照此执行。真正的风险不是技术，而是**前后端对 `Content-Type` 没有一致约定**——一方发 JSON、另一方等表单，就会静默失败。

### 坑 3：`rowCount()` 为 0 不代表记录不存在

- **现象**：对同一篇文章连续发送两次内容完全相同的 PUT 请求，接口返回"修改成功"，但打印 `$stmt->rowCount()` 得到 **0**。若以 `rowCount() === 0` 判定"记录不存在"，用户会收到 404——而他眼前的正是这篇文章。
- **原因**：MySQL 执行 `UPDATE` 分两步：

  1. 按 `WHERE` 条件**匹配**行（matched）
  2. 逐行比较新旧值，**不同的才真正写入**（changed）

  `rowCount()` 返回的是 **changed**，不是 **matched**。所以两种完全不同的情况都返回 0：

  | 情况 | matched | changed | `rowCount()` |
  |---|---|---|---|
  | id 不存在 | 0 | 0 | 0 |
  | id 存在，但新值等于旧值 | 1 | 0 | **0** |

  这**不是 MySQL 的 bug，是它的定义**：值没变就不算更新。

- **怎么修的**：把"存在性判断"和"更新操作"拆成两次查询，不再看 `rowCount()`。

  ```php
  // 1. 先确认记录存在
  $check = $pdo->prepare("SELECT id FROM articles WHERE id = ? AND deleted_at IS NULL");
  $check->execute([$id]);
  if ($check->fetch() === false) {
      http_response_code(404);
      // 返回 code 1002
      exit;
  }

  // 2. 再执行更新
  $stmt = $pdo->prepare("UPDATE articles SET title = ?, content = ?, status = ? WHERE id = ? AND deleted_at IS NULL");
  $stmt->execute([$title, $content, $status, $id]);
  ```

  存在性查询只 `SELECT id` 一列，走主键索引，代价很小。

- **取舍：多一次查询值不值？**

  | | 说明 |
  |---|---|
  | 成本 | 多一次数据库往返。主键单列查询，本地实测为微秒级 |
  | 收益 | 判断结果**确定**，不会把"内容没改动"误报成"记录不存在" |

  **为什么不用更省事的办法？** 有——连接时开启 `PDO::MYSQL_ATTR_FOUND_ROWS => true`，可让 `rowCount()` 返回 matched 而非 changed。但没有采用：

  1. 该选项是 MySQL 专属，换 PostgreSQL / SQLite 行为不同，代码不可移植
  2. 依赖一个隐藏的连接选项决定业务逻辑，读代码的人看不出来

  宁可多一次语义明确的查询。

- **如果重来会怎么避免**：写 `UPDATE` 之前先分清自己要回答哪个问题——"**改了几行**"用 `rowCount()`，"**记录在不在**"必须单独查。这两个问题不能用一个返回值同时回答。

### 如果只能修一条

**修第 1 条。** 无鉴权的管理端等于后台门户大开，修它的收益是其余所有项之和。

### 两条不做，但要说清为什么

**没做富文本编辑。** 见 5.3。开富文本等于开 `innerHTML`，在没有登录的项目里是给自己挖坑。要做得先有服务端白名单过滤。

**没做前后端同源部署。** 现在是 5500 / 8000 两个端口，靠 CORS 头放行。生产环境应该用 Nginx 把 `/api` 反代到后端，前端和后端同一个域名同源，CORS 头就可以整段删掉——**少一层配置就少一处出错的地方**。留在这里是因为本地开发用双端口更方便调试。
