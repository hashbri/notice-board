# 接口文档

- 基础路径（Base URL）：`/api`
- 数据格式：请求与响应均为 `application/json`
- 时间格式：`YYYY-MM-DD HH:mm:ss`
- 跨域：服务端已开启 CORS，允许任意来源（开发阶段配置）
- 统一响应结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

> `code = 0` 表示成功，非 0 表示错误（错误码表见文末）。
> `message` 为可直接展示给用户的中文文案，前端无需自行维护错误文案。

---

## 一、接口清单

所有接口都在 `/api` 下，但**分成两套前缀**：

| 前缀 | 使用者 | 读操作（GET）是否过滤草稿 |
|---|---|---|
| `/api` | 前台页面 | ✅ 强制 `status = 1`，草稿一律不可见 |
| `/api/admin` | 管理端页面 | ❌ 不过滤，草稿可见 |

两套前缀的路径、方法、请求体、校验规则**完全一致**，唯一差别是读操作是否过滤草稿。

> ⚠️ **`/api/admin` 不是安全机制。** 本项目没有登录功能，任何人访问 `/api/admin/` 都能读到草稿、甚至直接删改文章。它的作用是**数据隔离**——防止前台代码写错时把草稿露给访客。真正的访问控制要靠登录，见 `design.md` 第 5 节。

| # | 接口 | 方法 | 路径 | 说明 |
|---|---|---|---|---|
| 1 | 资讯列表 | GET | `/articles` | 前台分页查询，只含已发布 |
| 2 | 资讯详情 | GET | `/articles/{id}` | 前台单条查询，草稿返回 404 |
| 3 | 资讯发布 | POST | `/articles` | 新建 |
| 4 | 资讯修改 | PUT | `/articles/{id}` | 全量更新 |
| 5 | 资讯删除 | DELETE | `/articles/{id}` | 软删除 |
| 6 | 管理端列表 | GET | `/admin/articles` | 含草稿，草稿置顶 |
| 7 | 管理端详情 | GET | `/admin/articles/{id}` | 草稿也能读到（编辑回填用） |

**通用规则**

- 所有查询只处理未删除的记录：`deleted_at IS NULL`
- 只有前台的列表（1）和详情（2）额外要求 `status = 1`
- 写操作（3、4、5）在两种前缀下行为完全相同，`/api/admin/articles` 也能发 POST / PUT / DELETE
- 路径第一段不是 `articles` 时，统一返回 `404` + `1003 接口不存在`（如 `/api/hello/7`）

## 二、接口详情

### 2.1 资讯列表 · `GET /articles`

**请求参数（Query）**

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `page` | int | 否 | 1 | 页码，从 1 开始。传入小于 1 的值时按 1 处理 |
| `size` | int | 否 | 5 | 每页条数。合法范围 **1~50**，越界时**静默回落为 5** |

> `size` 越界不报错是刻意选择：它不属于"数据错误"，静默修正对调用方更宽容。代价是调用方不知道自己传错了——已列入 `design.md` 第 7 节已知不足第 5 条。
> 关键词搜索未实现。

**过滤与排序**

- 条件：`status = 1 AND deleted_at IS NULL`（草稿与已删除记录不返回）
- 排序：`created_at DESC, id DESC`。第二排序键用于避免同一秒发布的多条记录顺序不稳定

**响应示例**

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "total": 14,
    "page": 1,
    "size": 5,
    "list": [
      {
        "id": 20,
        "title": "hehe",
        "status": 1,
        "created_at": "2026-11-20 14:50:12"
      },
      {
        "id": 15,
        "title": "接口测试新增",
        "status": 1,
        "created_at": "2026-11-17 22:02:52"
      }
    ]
  }
}
```

| 字段 | 说明 |
|---|---|
| `total` | 符合条件的总条数（不受分页影响） |
| `page` | 当前页码（已按兜底规则修正后的值） |
| `size` | 每页条数（已按 1~50 的规则修正后的值） |
| `list` | 当前页数据，含 `id` / `title` / `status` / `created_at` 四个字段 |

> 列表不返回 `content`，避免一次传输大量正文。需要正文请调用详情接口。
> 总页数由前端按 `Math.ceil(total / size)` 计算，后端不重复算。

**错误情况**：本接口不返回业务错误。`page` 为 0、负数或非数字时按 1 处理；`size` 小于 1 或大于 50 时按 5 处理。

### 2.2 资讯详情 · `GET /articles/{id}`

**路径参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | int | 是 | 文章编号 |

**响应示例**

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": 12,
    "title": "本学期寒假放假时间通知",
    "content": "各位同学：\n本学期寒假自 2027 年 1 月 18 日开始……",
    "status": 1,
    "created_at": "2026-11-03 08:00:00",
    "updated_at": "2026-11-03 08:00:00"
  }
}
```

**错误情况**

| 情况 | HTTP | code | message |
|---|---|---|---|
| id 不存在 | 404 | 1002 | 文章不存在 |
| id 存在但为草稿（`status = 0`） | 404 | 1002 | 文章不存在 |
| id 已被软删除 | 404 | 1002 | 文章不存在 |

> 三种情况对外**返回完全相同的响应**，不区分“不存在”和“无权查看”，避免通过枚举 id 探测未公开内容是否存在。

### 2.3 资讯发布 · `POST /articles`

**请求体**

```json
{
  "title": "公告标题",
  "content": "公告正文",
  "status": 1
}
```

| 字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `title` | string | 是 | — | 标题 |
| `content` | string | 是 | — | 正文 |
| `status` | int | 否 | 0 | `0` = 草稿，`1` = 已发布 |

> 服务端通过 `file_get_contents('php://input')` 读取请求体。**必须携带请求头 `Content-Type: application/json`**，否则服务端无法解析，`$_POST` 为空。

**字段校验规则**

| 顺序 | 校验项 | 规则 | HTTP | code | message |
|---|---|---|---|---|---|
| 1 | 请求体格式 | 必须是合法 JSON 对象 | 400 | 1001 | 请求体不是合法 JSON |
| 2 | `title` | `trim` 后不为空 | 400 | 1001 | 标题不能为空 |
| 3 | `title` | 字符数 ≤ 100（按 `mb_strlen` 计，中文算 1 字） | 400 | 1001 | 标题不能超过 100 字 |
| 4 | `content` | `trim` 后不为空 | 400 | 1001 | 正文不能为空 |
| 5 | `status` | 只能是 `0` 或 `1` | 400 | 1001 | 状态只能是 0 或 1 |

> 校验按上表顺序执行，**遇到第一个失败即返回**，不累积全部错误。
> `title` 与 `content` 在校验前先做 `trim`，因此“只输入空格”会被判定为空。

**响应示例（成功）**

```json
{
  "code": 0,
  "message": "创建成功",
  "data": {
    "id": 17
  }
}
```

HTTP 状态码为 **201 Created**。

> `id`、`created_at`、`updated_at` 由数据库生成，请求中无需也无需提供。

### 2.4 资讯修改 · `PUT /articles/{id}`

**路径参数**：`id`（int，必填）

**请求体**：与 2.3 完全一致（`title` / `content` / `status` 三个字段）

| 字段 | 默认值 | 说明 |
|---|---|---|
| `status` | 1 | 与新增不同，修改时未传 `status` 按已发布处理 |

**校验规则**：与 2.3 的五条完全相同。

**更新语义：全量更新（PUT）**

- 三个字段均按请求体覆盖原值，**未传的字段不会保留原值**
- 不使用部分更新（PATCH）语义，调用方需提交完整数据

**存在性检查**

更新前先执行 `SELECT id ... WHERE id = ? AND deleted_at IS NULL`，查不到则返回 404。

> 不使用 `UPDATE` 的 `rowCount()` 判断记录是否存在。原因是 `rowCount()` 返回“实际改变的行数”，当提交的内容与原记录完全相同时返回 0，会被误判为“记录不存在”。

**响应示例**

```json
{
  "code": 0,
  "message": "修改成功",
  "data": {
    "id": 17
  }
}
```

**错误情况**

| 情况 | HTTP | code | message |
|---|---|---|---|
| 请求体不是合法 JSON | 400 | 1001 | 请求体不是合法 JSON |
| 字段校验失败 | 400 | 1001 | 见 2.3 校验表 |
| id 不存在或已删除 | 404 | 1002 | 文章不存在 |

**幂等性**：相同请求重复提交，第一次与后续均返回 `code = 0`，结果一致。

---

### 2.5 资讯删除 · `DELETE /articles/{id}`

**路径参数**：`id`（int，必填）

**请求体**：无

**删除方式：软删除**

服务端执行 `UPDATE articles SET deleted_at = NOW() WHERE id = ?`，**不从表中物理删除记录**。

| 效果 | 说明 |
|---|---|
| 数据仍在表中 | `deleted_at` 由 `NULL` 变为操作时间 |
| 列表查不到 | 所有查询均带 `deleted_at IS NULL` 条件 |
| 详情查不到 | 同上，返回 404 |
| 可恢复 | 将 `deleted_at` 置回 `NULL` 即可 |

采用软删除的原因：删除可回滚、操作可追溯、后续关联数据（如评论）不会变成孤儿记录。代价是所有查询必须记得带 `deleted_at IS NULL` 条件。

**响应示例**

```json
{
  "code": 0,
  "message": "已删除",
  "data": {
    "id": 17
  }
}
```

**错误情况**

| 情况 | HTTP | code | message |
|---|---|---|---|
| id 不存在 | 404 | 1002 | 文章不存在 |
| id 已被软删除（重复删除） | 404 | 1002 | 文章不存在 |

**幂等性**：第二次删除同一 id 返回 404，不会重复修改数据，也不会报错崩溃，符合 HTTP DELETE 的幂等语义。

### 2.6 管理端列表 · `GET /admin/articles`

与 2.1 的差别只有三处：

| | `GET /articles`（前台） | `GET /admin/articles`（管理端） |
|---|---|---|
| 过滤条件 | `status = 1 AND deleted_at IS NULL` | `deleted_at IS NULL`（**不过滤 status**） |
| 排序 | `created_at DESC, id DESC` | **`status ASC, created_at DESC, id DESC`** |
| `total` 含义 | 已发布条数 | 全部未删除条数（含草稿） |

参数 `page` / `size` 与 2.1 完全一致。

**为什么排序加了 `status ASC`**

草稿（`status=0`）全部排在已发布（`status=1`）之前。管理员一进管理端，第 1 页最上面就是所有待处理的草稿——**待办优先**，这是后台系统的常规做法。

代价：把一条草稿改成「发布」后提交，它会从第 1 页立刻消失（跳进已发布组，按时间重新排队）。这是排序规则的自然结果，不是 bug。

**响应示例**

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "total": 16,
    "page": 1,
    "size": 5,
    "list": [
      { "id": 19, "title": "haha", "status": 0, "created_at": "2026-11-20 14:23:18" },
      { "id": 13, "title": "（草稿）实验室设备采购清单第二轮", "status": 0, "created_at": "2026-11-02 09:00:00" },
      { "id": 20, "title": "hehe", "status": 1, "created_at": "2026-11-20 14:50:12" }
    ]
  }
}
```

前两条 `status` 均为 0，排在最前面。

**性能说明**：该查询的 `EXPLAIN` 结果是 `type=ALL` + `Using filesort`，即全表扫描，没走 `idx_list` 索引。原因、为什么现在不修、什么时候必须修，见 `design.md` 第 2.4 节。

### 2.7 管理端详情 · `GET /admin/articles/{id}`

与 2.2 的唯一差别：**不过滤 `status`**，草稿也能正常读到。

| 情况 | `GET /articles/{id}` | `GET /admin/articles/{id}` |
|---|---|---|
| id 不存在 | 404 / 1002 | 404 / 1002 |
| id 已软删除 | 404 / 1002 | 404 / 1002 |
| **id 是草稿** | **404 / 1002** | **200 / 0，正常返回** |
| 已发布 | 200 / 0 | 200 / 0 |

**这个接口存在的唯一理由**：管理端点「编辑」时要回填表单，而草稿必须能读到自己的标题、正文和 `status`。若复用前台详情接口，草稿会 404，编辑功能直接失效。

**实测对比**（`id=19` 是一条草稿，`content` 为 `ha'ha`）：

```
GET /api/articles/19        → 404  {"code":1002,"message":"文章不存在"}
GET /api/admin/articles/19  → 200  {"code":0,"data":{"id":19,"status":0,...}}
```

## 三、错误码表

| code | HTTP 状态码 | 含义 | 前端处理方式 |
|---|---|---|---|
| `0` | 200 / 201 | 成功 | 取 `data` 渲染 |
| `1001` | 400 | 参数错误 | 直接展示 `message` |
| `1002` | 404 | 资源不存在 | 展示 `message`，详情页可引导回列表 |
| `1003` | 404 | 路由不存在（路径第一段不是 `articles`） | 视为程序错误，不应出现在正常流程中 |
| `5000` | 500 | 服务端异常 | 提示“服务异常，请稍后再试”（**尚未实现**） |

> `1003` 已修正为返回 HTTP `404`（此前误返回 200）。实测 `/api/hello/7` → `404` + `{"code":1003,"message":"接口不存在"}`。
> **待补**：数据库连接失败等异常目前会把 PHP 的 HTML 错误信息直接输出，未包装为 `code 5000` 的 JSON 响应。已列入 `design.md` 第 7 节第 3 条。

**错误码编号规则**

- `0`：成功
- `1xxx`：客户端问题（参数、路径、资源不存在）
- `5xxx`：服务端问题
